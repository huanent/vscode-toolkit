# 前端渐进式重构计划

## 目标

彻底重构前端代码，但不一次性重写或切换所有功能。以 `webview/src_new` 为新的代码组织和实现目录，从 `webview/src` 逐步迁移功能，在保持现有功能可用的前提下，逐步淘汰旧代码。

最终删除旧的 `webview/src`，再将 `webview/src_new` 重命名为 `webview/src`，恢复统一的前端源码目录。

## 目录职责

- `src`：现有前端实现，继续承载尚未迁移的功能；随着迁移推进逐步缩减。
- `src_new`：重构后的前端实现，承载已经迁移的功能及其组件、状态逻辑和工具函数。
- 新旧目录仅在过渡期并存，不作为长期维护的双轨结构。

## 迁移原则

- 按功能逐步迁移，每次选择一个职责明确、能够独立验证的范围，不以整目录搬运代替重构。
- 先梳理当前功能行为和依赖，再在新结构中实现、接入和验证，最后清理对应的旧代码。
- 默认保持现有功能、交互和扩展端通信契约不变；必要的行为变更单独说明和验证。
- 页面和容器负责组合组件，复杂状态与副作用收敛到专用 Hook，纯业务逻辑放入工具模块。
- 按功能就近组织代码，只将确实复用的组件和工具提升为共享模块，避免过度抽象。
- 优先复用现有 UI 组件、`cn` 工具和 Tailwind CSS，使用 VS Code 主题变量，遵循仓库现有规范。
- 新旧代码间如需临时依赖，应明确后续移除方式，避免让新结构长期依赖旧实现。
- 不在迁移过程中顺带修改无关功能，确保每次变更范围清晰、可验证、可回退。

## 实施步骤

### 1. 确定本轮迁移范围

选择一个页面、功能模块或共享能力，确认其入口、组件、状态管理、样式、资源和扩展端通信依赖，并列出需要保留的行为与验证方式。

### 2. 在新结构中重构实现

将选定功能逐步实现到 `src_new`，按职责拆分组件、Hook 和工具函数。迁移应改善代码组织和维护性，而不是仅复制旧代码。

### 3. 接入并验证新实现

将对应入口或调用方切换到新实现；按需调整构建入口和导入路径，保证尚未迁移的功能仍可正常运行。

每轮迁移至少完成以下验证：

- 运行 `npm run build` 和 `npm run lint`。
- 运行受影响范围内的现有测试；对重要行为变更补充必要测试。
- 在实际 Webview 中检查主要交互、扩展端通信，以及适用的加载、空数据和错误状态。
- 涉及布局或样式时，检查不同面板尺寸与 VS Code 主题下的显示效果。

### 4. 淘汰对应旧代码

确认新实现已接入、验证通过，且旧实现没有剩余调用方后，删除被替代的组件、逻辑、样式和资源引用。仍被其他未迁移功能使用的共享代码暂时保留，待依赖迁移后再清理。

重复以上流程，逐步缩小 `src` 的职责与体积，直到所有需要保留的功能均由新实现承载。

### 5. 完成目录切换

最终切换前，确认：

- 所有需要保留的前端功能已迁移并接入新实现。
- 新实现不再依赖旧 `src` 中的代码或资源。
- 旧目录中的入口、共享代码和样式已完成替换，不存在遗漏功能。

满足条件后，在同一次收尾变更中完成：

1. 删除旧的 `webview/src`。
2. 将 `webview/src_new` 重命名为 `webview/src`。
3. 同步更新构建配置、TypeScript 配置、导入路径、测试及文档中的相关引用。
4. 检查并清理失效路径和临时兼容代码，确认没有仍依赖 `src_new` 路径的有效配置或代码。
5. 重新运行构建、Lint 和相关测试，并对受影响的 Webview 做回归检查。

## 完成标准

- 前端源码统一位于 `webview/src`，不再保留过渡目录 `src_new`。
- 旧实现及迁移期兼容代码已清理，未迁移功能没有被误删。
- 组件、状态逻辑、业务工具和共享能力职责清晰，符合仓库代码组织规范。
- 构建、Lint、相关测试和实际 Webview 回归验证通过。

本计划用于记录迁移方向与执行标准，不代表所有功能已完成迁移；实际进度以每轮已接入、已验证并完成旧代码清理的结果为准。
